## §S 遮蔽与绑定纪律

> **状态**: P0 — 基础级（名称解析必须确定性以保证跨 AI 一致性）
> **依赖**: core@1.0, §0 元规则, Law I（指纹唯一性）, Law VI（向后兼容性）
> **验证器**: `check_shadowing(module)` — 铁律式检查（见 §S.7）

---

### S.1 动机

AI 代理从多个包解析名称。两种失败模式会破坏 ΣLang 的确定性：

1. **静默替换** — 用户包重新定义 `⊕` 而未声明；两个 AI 读取同一规范却解析出不同语义。
2. **导入顺序依赖** — `import A` 然后 `import B` 与 `import B` 然后 `import A` 对同一名称产生不同含义。两者都必须是不可能的。

同时，包需要**本地命名自由**：张量包可能合法地想要一个本地的类似 `⊕` 的名称，而不干扰全局数学命名空间。

ΣLang 的答案：将**符号身份**与**名称绑定**分离，并对可遮蔽性进行分级。

---

### S.2 双层模型

#### S.2.1 符号（身份层）

- 符号是语义原子（元规则 1：符号首位性）。
- 通过指纹全局唯一（Law I）。一旦发布不可变（Law VI）。
- **绝不可重定义，绝不可遮蔽**——无论级别如何。

#### S.2.2 绑定（解析层）

- 绑定是在某个作用域内有效的映射 `name → symbol`。
- 绑定可被**遮蔽**（重新绑定到另一个符号）——但只能按以下规则进行。
- 原始符号始终可通过其**限定名**访问（逃生舱，§S.4 R2）。

> 这保留了元规则 2（无同义词）：一个*符号*恰好有一个语义。
> 遮蔽重新绑定的是*名称*；它绝不重新定义*符号*。

### S.3 遮蔽类别

| 类别 | 覆盖范围 | 可遮蔽？ | 需要声明？ | 示例 |
|------|---------|---------|-----------|------|
| **不透明** | core@1.0 常量 + 所有数学域符号 | ❌ 否（错误） | — | `ℕ`, `𝔹`, `π`, `⊕`, `∫`, `∂`, `ℝ` |
| **可遮蔽** | 非数学域符号（金融、AI、中医……） | ✅ 是 | ✅ 是（`shadow`） | `finance.base.Δ`, `tcm.wuzang.心` |
| **自由** | 非符号语义：类型名、函数/操作名、变量、标签 | ✅ 是 | ✅ 是（信息性） | `combine`, `Tensor`, `consensus` |

#### S.3.1 不透明 — 定义

```md
不透明 ::= 核心常量 | 数学域符号

核心常量 : core@1.0 定义的任何符号
数学符号 : 声明为 Domain: math 的包导出的任何符号（声明式 — 见 §S.4 R6）
```

#### S.3.2 自由 — "非符号语义"的定义

非符号语义 = 携带含义但不是 Sym 原子的标识符：类型构造器（`Tensor⟨·,·⟩`）、函数名（`combine`）、变量、标签。它们可遮蔽但遮蔽**仍必须声明**——隐式遮蔽是 bug 来源。

### S.4 规则

#### R1 — 显式声明
每个遮蔽必须用 `shadow` 关键字声明（§S.5）。未声明的名称冲突是 Verifier 错误，而非静默解析。

#### R2 — 逃生舱（限定名）
每个符号无论遮蔽与否均可通过限定名访问：

```md
finance.greeks.Δ    # 始终解析到原始符号
math.base.⊕         # 即使 ⊕ 被本地遮蔽
```

限定名**绝不**可遮蔽。

#### R3 — 确定性解析（导入顺序无关）
解析优先级固定，按此顺序：

```text
1. 本地显式遮蔽（当前包中声明）   → 胜出
2. 导入绑定（按包声明的导入顺序）   → 次之
3. core@1.0                       → 始终可用
```

同层名称冲突（两个导入暴露同一名称，无本地遮蔽）是**歧义遮蔽** → Verifier 错误。绝不猜测，绝不依赖导入顺序。

#### R4 — 不传播
遮蔽是声明它的包（或作用域）的本地行为。导入该包的下游包**不继承**其遮蔽。一个包的本地决定不能污染依赖树。

#### R5 — 数学域是单一命名空间
在数学域内，名称冲突（如 `math.calculus.δ` vs `math.linear.δ` 具有不同语义）是**定义错误**——包必须重命名，而非遮蔽。数学绝不进入遮蔽机制。

#### R6 — 域是声明式的，非硬编码的
`Domain: math` 是包头声明，而非包名的字符串匹配。包可以自愿进入不透明类别（`Opaque: true`）以保护其符号。Verifier 检查声明与导出符号类型的一致性。

#### R7 — 自由类遮蔽也要声明
类型/函数/变量遮蔽使用相同的 `shadow` 语法。不需要理由，但声明必须存在。Verifier 对每个声明的自由类遮蔽发出**警告**（R7-warning）：验证仍然通过，但遮蔽在报告中被标记——推动作者使用新名称，同时保留遮蔽自由。

#### R8 — 可审计性
Verifier 发出**遮蔽报告**：每个遮蔽点（名称、原始符号、新符号、作用域）。业务逻辑保持数学上可审计。

### S.5 语法

```md
# Package: tensor.net
# Version: 0.1.0
# Domain: ai
# Opaque: false
# Depends: core@1.0, math.base@1.0, finance.base@1.0

## Imports
import core
import math.base
import finance.base

## Shadowing
# R2: 逃生舱 — 限定名保留
shadow finance.base.Δ → as finance_Δ
# R1: 导入符号的本地重新绑定（仅可遮蔽类）
shadow combine
# R7: 自由类遮蔽（函数名）
shadow tensor_add → local_add
# v0.2（保留）: shadow combine scope: <fn|section> — v0.1 仅为包级别
```

#### S.5.1 文法

```text
遮蔽声明 ::= "shadow" 限定名 ["→" ["as"] 标识符]
           | "shadow" 标识符 ["→" 标识符]
限定名   ::= 包名 "." 符号名
```

### S.6 解析算法（参考）

> v0.1: `scope` 是**包**。更细粒度的作用域（函数/节）保留给 v0.2，
> 通过 `shadow` 声明上的可选 `scope:` 参数。

```text
resolve(name, scope):
  if scope 对 name 有显式遮蔽:        return shadow.target        # R1
  if 限定名:                          return package.symbol       # R2, 永不遮蔽
  candidates = 暴露 name 的导入列表
  if len(candidates) == 1:            return candidates[0]        # 确定性
  if len(candidates) > 1:             → 歧义遮蔽错误              # R3
  if name in core@1.0:                return core.symbol          # 不透明，始终
  → 未解析错误
```

### S.7 Verifier 集成

铁律流水线中的新检查（镜像 `impl/verifier/src/main.rs` 中现有的 `check_*`）：

```text
fn check_shadowing(module) -> violations:
  R1  每个 `shadow` 目标指向现有绑定（可遮蔽/自由类）
  R3  无歧义遮蔽（同层冲突）
  R4  遮蔽目标在当前包作用域内解析
  R5  无数学院符号被遮蔽（不透明类）
  R6  Domain/Opaque 头声明一致
  output: shadow_report[]  (+ R7-warnings[])
```

Verifier JSON 输出扩展：

```json
{
  "spec": "tensor.net@0.1.0",
  "pass": true,
  "shadowing": {
    "report": [
      {"name": "Δ", "from": "finance.base.Δ", "to": "finance_Δ", "scope": "tensor.net"}
    ],
    "warnings": [
      {"name": "tensor_add", "class": "free", "scope": "tensor.net", "reason": "R7-warning"}
    ],
    "opaque_shadow_attempts": 0
  }
}
```

### C.3 常量规则

1. **不透明** — 遮蔽或重定义任何 §C 常量是 Verifier 违规（§S R5 族）。
2. **无同义词** — 常量不得以第二字形导出（元规则 2）。
3. **精度** — 实现必须遵守声明的精度边界（Law VIII；E-08 候选）。
   以上参考值带有精确性注释（SI 精确 vs CODATA 导出）。
4. **单位** — 物理常量携带单位元数据；单位是语义定义的一部分，而非装饰性文本。
5. **新常量** — 新增遵循 RFC → 注册表路径（§Z）；以上前缀已保留。

## §G 冲突裁决流程（E-07，于 2026-08-01 推广）

> **状态**: 元规则 — 规范治理。补充 Law I：指纹必须唯一，当不唯一时，这是解决路径。治理而非代码：Verifier 拒绝认证未解决的冲突；注册表记录结果。

### G.1 范围

适用于：

- **指纹冲突** — 两个包声明相同指纹（Law I 违规）。
- **语义争端** — 符号含义在包间存在争议（元规则 2）。
- **限定名冲突** — 导入暴露相同名称而无声明遮蔽（§S R3）。

### G.2 解决路径

```md
1. RFC 提交 — 冲突描述 + 双方证据（模板 §G.3）。
2. 仲裁评审 — 人类委员会 + 双验证器交叉检查（Law XIII）。
3. 裁决记录在注册表中（胜者保留指纹；败者重新分配）。
4. 争议期间旧版本保持可加载（Law VI 有效；争议不冻结它们）。
```

### G.3 RFC 模板

```md
# RFC: 指纹/语义冲突

- 争议的指纹或符号: `0x…` / `字形`
- 涉及的包: `pkg_a@ver` vs `pkg_b@ver`
```
